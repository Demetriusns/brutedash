# Council review 2026-11-01 — PLAIN-LANGUAGE UX verdict (brutedash / Project Orion)

Reviewer lens: would a non-technical home / small-business user understand every screen, banner, alert, and button? User-facing copy must be casual, plain-spoken, non-technical; doctor metaphor is internal only.
Scope read: `app.py`, `README.md`, `PRODUCT.md`, `netmon/dashboard.py` (the dashboard — this repo has no HTML template files for it; `templates/` at repo root holds scanner check files, not pages), `netmon/templates.py`, `netmon/explainer.py`, `netmon/notify.py`, `netmon/weekly.py`, `netmon/reporting.py`, `netmon/playbooks.py`, `netmon/escalate.py`, `netmon/amass.py`, `netmon/nuclei.py`.
Git HEAD verified: `af51f64`.
Context that matters: no UX fix batch has landed since the 2026-10-18 verdict — every commit since is security, robustness, or dependencies. Findings 1–9 below are therefore verified carry-overs, re-checked line-by-line at today's HEAD, not re-inventions. One 2026-10-18 finding is genuinely fixed and is listed under Non-findings.

## Critical

None. Nothing on the main dashboard actively misleads a user about safety or destroys data without any warning at all. The High items below are dead-ends and a technician-only front door, not false reassurance.

Until a control exists, reword every dead-end to name a person, not a file: `Ask whoever set up this monitor to add an administrator email in the setup file, then try again.` Never show `BRUTEDASH_RESPONSE_ADMIN_EMAIL`, `OPENAI_API_KEY`, `auth.viewer_password`, or dotted keys like `response.admin_email` as the primary instruction.

### 2. [High] app.py — the Phase-1 demo front door is technician-only end to end (carried over as UX H2 on 2026-10-25, still unfixed)
User sees:
- `app.py:331`: heading `brutedash — mini SOC analyst`; `app.py:332`: `Paste an SSH auth log below, hit Analyze.` The form is pre-filled with the whole raw sample log (monospace, dark terminal styling, `app.py:320-327`) — a wall of log lines is literally the first screen.
- Results, `app.py:341-354`: columns `IP / Failed attempts / Severity` with the raw words `Medium`/`High` (not the dashboard's plain `Needs attention`/`Worth a look`), a `repeat attacker` tag, and a `Generate brief` button — "brief" is never explained.
- Brief page, `app.py:371-377`: `Technical brief: {{ ip }}`, a line reading `origin: llm` (or `rule-based`), then a `<pre>` block headed `Observed pattern:` / `Recommended actions:`.
- The rule-based brief itself, `app.py:178-184`: `Consistent with a brute-force attack.` and actions `Block the IP at the firewall (or fail2ban).` / `Review and rotate credentials on targeted accounts.`
Why it fails the bar: SOC, SSH, auth log, IP, fail2ban, firewall, rotate credentials, llm — none of it is translated, and none of it matches the netmon dashboard's vocabulary for the same ideas. README.md:3 repeats the pitch (`A mini SOC analyst for a home network`) to exactly the reader who cannot decode it. A home user landing here — the repo's public front door — cannot say what the tool did or what to do next.
Concrete fix: Heading `brutedash — who tried to break in, in plain English`; intro `Paste a sign-in log from a computer (the kind that records failed SSH sign-ins) below, then hit Analyze. The sample log is already filled in — just hit Analyze to see it work.` Results columns: `Address / Failed sign-ins / How serious` with the dashboard's severity words. Button `Explain this one`; brief heading `What happened: <address>`, drop the `origin:` line entirely (or `Written by the AI` / `Written by the monitor`), and rewrite the fallback actions as: `Block this address in your router or firewall settings.` / `Check whether any sign-in from this address ever succeeded.` / `Change the passwords on the accounts it tried.`

## Medium

### 3. [Medium] Bare MITRE codes as badges, hover-only jargon tooltip — carried over, still unfixed
User sees: `netmon/dashboard.py:1053` (main alert list) and `netmon/dashboard.py:1660` (case timeline): a badge whose entire visible text is `T1046` (etc.), with tooltip `Application Layer Protocol: Web Protocols — tactic: Command and Control`. Downloads copy repeats it at `netmon/dashboard.py:803`: `incidents with MITRE tags, what you did about them…`.
Why it fails the bar: a code with no words is decoration to a home user, tooltips do not exist on touch devices, and the tooltip "translation" is itself jargon. Nothing on the page ever says what MITRE is or why the code is shown.
Concrete fix: badge text becomes the plain label, code demoted: `Known attacker trick · T1046`; keep the bare code only inside the compliance download, where a technical reader (insurer/auditor) actually wants it, and change :803 to `a record of what happened, what you did about it, alert counts, and your score history.`

### 4. [Medium] Tool brand names (Amass / Nuclei) unexplained, and the "not installed" notes order the user to run developer commands — carried over, still unfixed
User sees: `netmon/dashboard.py:702`: `What the internet sees is the outside view (via Amass, optional)`; `netmon/dashboard.py:778-779`: heading `Deeper check (Nuclei)` and `Nuclei runs thousands of known vulnerability checks…`. When the tools are missing, the dashboard renders these notes verbatim:
- `netmon/amass.py:136-141`: `Amass is not installed -- it is optional. Install it to map what the internet sees of your domain(s): go install github.com/owasp-amass/amass/v4/...@latest (needs Go), or on Kali sudo apt install amass. Then list your own domain(s) under amass.domains in config.yaml.`
- `netmon/nuclei.py:127-132`: `Nuclei is not installed -- it is optional. Install it for deeper vulnerability checks of your own network: download the release for your system from github.com/projectdiscovery/nuclei/releases and put the binary on your PATH (or go install github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest).`
- When found, both also leak a raw file path into the note: `netmon/amass.py:133-134` / `netmon/nuclei.py:124-125`: `Amass found … at /home/…/amass` — a log line, not a sentence.
Why it fails the bar: "Amass" and "Nuclei" are names, not explanations — the user cannot tell what either does, whether it is safe, or whether they need it. The fallback then asks the least technical user in the product to use a terminal, Go, Kali, apt, and PATH editing. This remains the most technical paragraph in the product.
Concrete fix: headings/copy name the job, not the tool: `What the internet sees (a check of public records about your domain name, optional)`; `Deeper check (a free scanner that tests for known flaws)`. Missing-tool note becomes: `The outside-view check isn't set up on this box. It's optional — everything else keeps working. Whoever installed the monitor can add it later.` Delete the go/apt/PATH instructions from user-facing notes entirely (they belong in INSTALL.md); drop the binary path from the "found" note.

### 5. [Medium] "Escalate to admin" assumes an administrator the home user doesn't have — carried over, still unfixed
User sees: button `escalate to admin` (lowercase, unlike the neighbouring `close case`) at `netmon/dashboard.py:1632`; badge `awaiting admin` at `netmon/dashboard.py:1628` and `:1656` (`escalated to <email> · <when>`); confirm dialog at `netmon/dashboard.py:1694`: `This packages the whole case -- timeline, what was found, what you already tried -- and emails it to the admin address in your config. The case will show as "awaiting admin" until it is closed.` The playbook version is `Escalate to admin` at `netmon/dashboard.py:2915-2919`.
Why it fails the bar: in the target install the owner IS the only person. Who is "your administrator"? Where does the email go? The UI never says — and by default no admin address exists (finding 1), so the feature reads as sending your problem to an unnamed third party. "In your config" names no place the user can picture.
Concrete fix: button `Email this case to my helper`; badge `Emailed — waiting for a reply`; confirm: `This sends the whole case — timeline, what was found, what you already tried — to the helper email address in Settings. The case stays marked as waiting until you close it.` Pair with finding 1's Settings field so the address is visible where the button lives.

### 6. [Medium] "pcap", "Wireshark" and "forensic" used as if the user already speaks capture files — carried over, still unfixed
User sees: footer link `Analyze a pcap file` (`netmon/dashboard.py:904`); page heading and intro `netmon/dashboard.py:2355-2357`: `Analyze a pcap file` / `Upload a .pcap (e.g. exported from Wireshark). It runs through the same pipeline: flows, detection rules, and a plain-English AI explanation.`; results heading `netmon/dashboard.py:2367`: `pcap results: <filename>` with `<n> packets processed.`; case-timeline link `netmon/dashboard.py:1668`: `download packets from this case's window (.pcap)` + `raw packets from the forensic buffer -- opens in Wireshark`; Reports heading `netmon/dashboard.py:813`: `Forensic rewind` with only a `Loading...` box under it — the plain explanation exists only inside the JS off-state message (`netmon/dashboard.py:1767`), so a user with the feature ON never sees any explanation, just segment counts and megabytes (`netmon/dashboard.py:1775` also offers `download the last hour (.pcap)`).
Why it fails the bar: nothing ever says what a pcap is, where one comes from, or why a home user would have one. "Forensic" is investigator jargon, and the one heading every user sees is the one piece of copy that explains nothing.
Concrete fix: heading/link `Look at a saved traffic recording`; intro `If another tool (like Wireshark) saved a recording of network traffic as a .pcap file, upload it here and the monitor will explain what was happening in plain English.` Case link: `download the recording from this case's time window (for a technical helper to open)`. Results: `What the recording shows: <filename>` / `<n> packets looked at.` Rename :813 to `Traffic recording` and add a static line under it, always rendered: `Keeps a short rolling recording of traffic so you can download what happened just before an alert. It stays on this box.`

### 7. [Medium] The same severity and the same state get two or three different vocabularies depending on the panel — carried over, still unfixed
User sees: the main alert list translates severity — `[Needs attention] <title>` via SEV_WORDS (`netmon/dashboard.py:1050`) — but device alert history (`netmon/dashboard.py:1273`), threat-intel lookup results (`netmon/dashboard.py:1383`), case timelines (`netmon/dashboard.py:1659`), and the pcap results page (`netmon/dashboard.py:2378`) all render the raw word: `[High] <title>`. Separately, every main-list alert carries a raw status chip `[new]` / `[acknowledged]` / `[dismissed]` (`netmon/dashboard.py:1052`), while the button that sets it says `Mark seen`, the filter above the list says `Acknowledged` (`netmon/dashboard.py:688`), and the Settings rule-health table heads a column `Acknowledged` (`netmon/dashboard.py:1486`) — three names for one state on one screen.
Why it fails the bar: the plain severity words were the fix that made the main list readable; four other render paths quietly kept the old vocabulary, so the user must learn both and guess they are the same thing. `[acknowledged]` in brackets reads like a system code, not a state a person chose.
Concrete fix: use SEV_WORDS in all five render paths. Replace the status chip with words matching the buttons: `Not seen yet` / `Seen` / `Dismissed` — or drop the chip when the status is new and show only `Seen`/`Dismissed`.

### 8. [Medium] "Probation" device badge is never explained anywhere (flagged as staged in the 2026-10-25 synthesis; verified still unexplained)
User sees: a banner over the Devices table, `netmon/dashboard.py:1213`: `🟡 N devices on 24h probation watch`, and a per-device status badge, `netmon/dashboard.py:1218`: `🟡 Probation · trusted in 13.5h` (opposite `✅ Trusted`). The only note on the Devices section (`netmon/dashboard.py:755`) says `Name your devices so alerts read like English instead of hardware addresses.` — it never mentions probation.
Why it fails the bar: "probation" is a word from the criminal-justice system applied to the user's own TV or phone, with no sentence anywhere saying what the device did (nothing — it is simply new), what changes while it lasts, or what "trusted in 13.5h" will mean when it ends. A new user meets this badge on day one, for every device they own.
Concrete fix: badge `🟡 New — being watched closely for the first 24h`; banner `N new devices — the monitor watches new devices extra closely for their first 24 hours.` Add one static line under the Devices heading: `New devices are watched extra closely for their first 24 hours while the monitor learns what's normal for them. Nothing is blocked — it's just watching.`

### 10. [Low] netmon/dashboard.py:874, :872, :1599-1608 — "Prune now": permanent deletion behind a jargon verb, one click, no confirmation (carried over, still unfixed)

The panel's own explanation (:872) is about database mechanics (`deletes expired rows in small batches so the database never locks up`), not about what the user loses.

### 11. [Low] netmon/dashboard.py:1059, :1662 — "Follow-up ID" is an unexplained hex string on every alert (carried over, still unfixed)
User sees: `Follow-up ID: 9f3ac41be207…` on every main-list alert and every timeline entry, with no hint what it is for. It looks like an error code or something the user must save, and it adds a line of noise to the highest-frequency surface in the product.
Fix: label its purpose and truncate: `Reference code (only needed if you email this case to a helper): 9f3a…` — or remove it from the alert card and keep it only inside the case timeline.

### 12. [Low] Error banners paste programmer text and (mostly) give no next step — carried over, pattern unchanged
User sees (pattern, ~12 sites): the refresh banner `netmon/dashboard.py:1139-1141` does reassure (`Dashboard refresh hit a snag: <raw JS exception text> — the monitor keeps recording; this is a display hiccup. Retrying…`) but still pastes the exception; the loader failures do not even reassure: `Could not load assets: server returned 500`, `Could not load attack surface: …`, `Could not load external scan: …` — every loader builds its error from `throw new Error("server returned " + r.status)` (e.g. `netmon/dashboard.py:1206, :1252, :1291`, and peers throughout) and renders the message verbatim into a red banner.
Why it fails the bar: "server returned 500" and exception strings are log output, not guidance. The user learns something failed but not whether it matters, whether data is safe, or what to do.
Fix: one shared shape for every loader failure: `Couldn't load <thing> just now — the monitor is still recording. This usually clears on its own; if it keeps happening, restart the monitor.` Log the exception to console only, never into the banner.

### 13. [Low] Settings health tables still speak status-code, and scanner findings lead with slugs and CVE numbers — carried over, still unfixed
User sees: deeper-scan findings show a raw template slug + CVE string under each finding name (`netmon/dashboard.py:2068`: `<template_id> · CVE-2021-…`), with fallback text `See the finding name above.` when there is no description; self-check badges read raw `ok` / `drift` (`netmon/dashboard.py:2126`); pipeline-health badges read raw `ok` / `stale` / `unknown` (`netmon/dashboard.py:2150-2156` region, `renderPipelineHealth`); software-check rows lead with `CVE-…` and `fix-by <date>` (`netmon/dashboard.py:2189`), and the section header line says `${sw.packages} programs inventoried, ${sw.kev_entries} known-exploited flaws on the list` (`netmon/dashboard.py:2184`).
Why it fails the bar: "drift" in particular is pure insider vocabulary — a user cannot act on a check whose status is a word they have never seen. CVE numbers are fine as secondary reference; as the headline identifier they are a wall.
Fix: map badges to words at render: ok → `Fine`, drift → `Changed since first check`, stale → `Quiet too long`, unknown → `No data yet`. Demote template_id/CVE to small grey reference text after the plain description; replace the `See the finding name above.` fallback with `No plain description for this one yet — the name above is what the scanner calls it.`; :2184 → `<n> programs checked, <n> flaws on the list of flaws attackers are actively using.`

- (d) Digest email subject, `netmon/notify.py:538-539`: `[netmon] Digest: 5 alerts across 3 kinds` — alerts do not come in "kinds" in any user-facing vocabulary. Fix: `…5 alerts of 3 different types`.
- (e) NEW — whole-network banner, `netmon/dashboard.py:673` and `:1014`: `Whole-network view: this computer is relaying the LAN, so every device's traffic is monitored.` "LAN" and "relaying" are unexplained, in a banner whose whole job is reassurance.
